# **ARCHITECTURE.md — משחק סיימון (Simon)**

## **1\. מחסנית טכנולוגיה שנבחרה**

### **1.1 סיכום הסטאק**

### **1.2 החלטות טכנולוגיות מרכזיות**

* **TypeScript ללא React:** נבנה ממשק קטן עם שני מסכים ומספר מוגדר של מצבי משחק. Vanilla TypeScript מספיק לכך, ומונע הוספת שכבת רכיבים ותלויות שאינן נחוצות. React תהיה חלופה סבירה אם המוצר יתרחב למכלול מורכב יותר, אך לא בגרסה הנוכחית.  
* **Vite במקום תהליך בנייה ידני:** מספק סביבת פיתוח ובניית Production סטטית עם מעט תצורה. לפי התיעוד, `vite build` מפיק חבילה שמתאימה לאירוח סטטי. \[1\]  
* **`vite-plugin-pwa` במקום כתיבת Service Worker מאפס:** מפשט יצירת Manifest, Service Worker ושמירת משאבים לשימוש Offline. יש להגדיר במפורש את המשאבים הקריטיים שיישמרו מראש. \[2\]\[3\]  
* **Web Audio API במקום ספריית אודיו:** ארבעת הצלילים פשוטים, וניתן ליצור אותם באמצעות צמתי Oscillator/Gain. כך אין צורך להוריד קובצי שמע, והצלילים זמינים גם במצב Offline. ה-API זמין באופן רחב בדפדפנים מודרניים. \[4\]  
* **`localStorage` במקום Database או IndexedDB:** הנתונים קטנים ומובנים כרשומות משחק, ולכן `localStorage` מספיק. הוא נשמר בין הפעלות הדפדפן, אך הוא מקומי למקור (Origin) ולדפדפן, ואינו מסנכרן נתונים בין מכשירים. ייתכן מצב שבו הגישה אליו נכשלת. \[5\]  
* **GitHub Pages במקום Vercel או שרת:** האתר הוא Frontend סטטי בלבד. GitHub Pages ו-GitHub Actions מאפשרים בנייה ופריסה אוטומטיות מה-Repository, ללא Backend. יש להגדיר את `base` של Vite בהתאם לכתובת הפרויקט ב-GitHub Pages. \[6\]\[7\]

### **1.4 סיכונים ומגבלות**

* **אחסון מקומי:** ניקוי נתוני הדפדפן, שימוש במצב פרטי או החלפת דפדפן/מכשיר עלולים לגרום לאובדן ההיסטוריה. אין גיבוי או סנכרון.  
* **מגבלות דפדפן:** התקנת PWA והתנאים להצגת בקשת ההתקנה משתנים בין דפדפנים ומערכות הפעלה. האתר צריך לפעול כאתר רגיל גם אם התקנה אינה מוצעת.  
* **הפעלת שמע:** השמעת שמע עשויה להיות חסומה עד לאינטראקציה של המשתמש. יש ליצור או להפעיל את `AudioContext` בעקבות לחיצה על "התחל", ולבדוק את ההתנהגות במכשירי iOS ו-Android. \[4\]  
* **עדכוני PWA:** Service Worker עלול להמשיך להגיש גרסה שמורה עד להשלמת עדכון. יש להגדיר מדיניות עדכון ברורה ולבדוק שלא נוצרת תערובת של קבצים מגרסאות שונות.  
* **GitHub Pages:** מתאים לאתר סטטי ולא להרצת Backend. יש לו מגבלות שימוש, והוא אינו מיועד לאתרי מסחר או ל-SaaS. עבור משחק אישי קטן, אתר סטטי הוא התאמה טובה. \[8\]

## **2\. ארכיטקטורת מערכת**

### **2.1 מבט כללי**

המערכת היא אפליקציית אינטרנט סטטית שרצה כולה בדפדפן. אין Backend, Database, Authentication, API חיצוני או שירות AI.

```
GitHub Repository
       │ Push ל-main
       ▼
GitHub Actions
  ├─ התקנת תלויות
  ├─ בדיקות לוגיקה
  ├─ Vite Build
  └─ פרסום תיקיית dist
       │
       ▼
GitHub Pages (HTTPS)
       │ טעינה ראשונה / עדכון
       ▼
דפדפן במכשיר נייד
  ├─ UI: מסך בית / מסך אודות
  ├─ Game Engine: רצף, שלבים, ניקוד ומצב משחק
  ├─ Audio Module: Web Audio API
  ├─ Storage Module: localStorage
  └─ Service Worker + Cache: שימוש Offline
```

### **2.2 חלוקה למודולים**

#### **מודול ממשק משתמש (UI)**

אחראי להצגת שני המסכים בלבד:

* **מסך בית:** לוח ארבעת הצבעים, מצב/שלב המשחק, הניקוד וכפתור "התחל".  
* **מסך אודות:** השיא האישי והיסטוריית המשחקים.  
* **מצב סיום בתוך מסך הבית:** הודעת כישלון או ניצחון, ניקוד סופי ואפשרות להתחיל משחק חדש. מצב זה אינו מסך ניווט שלישי.

כל הטקסטים יהיו בעברית, והפריסה תהיה RTL ו-Mobile-First.

#### **מודול מנוע המשחק (Game Engine)**

אחראי לכללי המשחק ואינו תלוי ב-DOM:

* יצירת רצף אקראי.  
* התחלת המשחק עם צבע אחד.  
* הוספת צבע אחד לרצף לאחר הצלחה בשלב.  
* ניהול של עד 10 שלבים.  
* בדיקת לחיצות המשתמש מול הרצף.  
* חסימת קלט בזמן הצגת הרצף.  
* הוספת נקודה לכל צבע ששוחזר נכון, גם אם המשתמש טועה בהמשך אותו שלב.  
* סיום מיידי בטעות הראשונה, או ניצחון לאחר השלמת השלב העשירי.

מצבי המשחק הלוגיים המומלצים: `idle`, `showing-sequence`, `awaiting-input`, `failed`, `won`. יש לרכז את המעברים בין המצבים בלוגיקת המשחק, כדי למנוע קלט במצב לא תקין.

#### **מודול אודיו (Audio Module)**

* יוצר `AudioContext` אחד ומשתמש בו לאורך המשחק.  
* מקצה תדר/צליל ייחודי לכל אחד מארבעת הצבעים.  
* מפעיל את הצליל יחד עם הדלקת הצבע.  
* מספק צלילי משוב להצלחה ולכישלון.  
* מפעיל/מחדש את `AudioContext` בעקבות אינטראקציה מפורשת של המשתמש, לפי מגבלות הדפדפן.

#### **מודול אחסון (Storage Module)**

* קורא וכותב את היסטוריית המשחקים והשיא האישי דרך `localStorage`.  
* מרכז את שמות המפתחות ואת פעולות הקריאה/כתיבה במקום אחד.  
* מבצע ניתוח (Parsing) ובדיקת מבנה לנתונים שנקראו, לפני השימוש בהם.  
* מטפל בשגיאות קריאה/כתיבה ומאפשר להמשיך לשחק גם אם השמירה אינה זמינה, תוך הצגת הודעה מתאימה.

#### **מודול PWA**

* כולל Web App Manifest עם שם האפליקציה, סמלים, צבעי תצוגה ו-`start_url` מתאים.  
* Service Worker שומר מראש את קובצי ה-HTML, JavaScript ו-CSS, את סמלי האפליקציה וכל משאב מקומי חיוני.  
* אין להסתמך על גופנים, תמונות, ספריות או קובצי שמע שמגיעים מ-CDN חיצוני בזמן ריצה.  
* עדכון גרסה יחליף את המטמון באופן מבוקר, בלי להשאיר את האפליקציה במצב שבו קובצי JavaScript ו-HTML אינם תואמים.

### **2.3 מודל נתונים ואחסון מקומי**

אין Database. כל הנתונים נשמרים ב-`localStorage` של מקור (Origin) האתר.

#### **רשומת משחק**

כל משחק שהסתיים נשמר כרשומה:

| שדה | סוג מומלץ | משמעות |
| ----- | ----- | ----- |
| `id` | string | מזהה מקומי ייחודי לרשומה. |
| `endedAt` | string בפורמט ISO 8601 | תאריך ושעת סיום המשחק. |
| `score` | number | מספר הלחיצות הנכונות שנצברו במשחק. |
| `finalLevel` | number | השלב שבו המשחק הסתיים. |
| `result` | `won` או `lost` | ניצחון או כישלון. |

#### **מפתחות אחסון**

* `simon.gameHistory.v1` — מערך רשומות המשחקים.  
* `simon.bestScore.v1` — שיא אישי מספרי.

יש לשמור את הרשומה פעם אחת בלבד לכל משחק. יש למנוע שמירה כפולה עקב לחיצות חוזרות או הפעלה כפולה של מצב הסיום. במקרה ניצחון, `finalLevel` יהיה 10; במקרה כישלון, הוא יהיה מספר השלב שבו התרחשה הטעות.

היסטוריית המשחקים יכולה לגדול עם הזמן. בגרסה הראשונה ניתן לשמור את כל הרשומות בהתאם ל-PRD; אם יתגלה צורך בהגבלת גודל, יש להגדיר מדיניות מפורשת ולא למחוק היסטוריה בשקט.

### **2.4 זרימת נתונים**

#### **התחלת משחק**

1. המשתמש לוחץ על "התחל".  
2. ה-UI מבקש מה-Game Engine לאתחל משחק חדש.  
3. הניקוד, השלב והרצף הקודם מתאפסים.  
4. נוצר צבע ראשון אקראי.  
5. ה-Game Engine עובר ל-`showing-sequence` ומורה ל-UI ול-Audio Module להציג ולהשמיע כל צבע בתורו.  
6. בסיום הרצף הוא עובר ל-`awaiting-input` ומאפשר לחיצות.

#### **שחזור רצף**

1. לחיצה על צבע מתקבלת רק במצב `awaiting-input`.  
2. ה-Game Engine משווה את הצבע שנבחר לצבע הבא ברצף.  
3. אם נכון, הניקוד עולה באחד ומתקדמים למיקום הבא ברצף.  
4. אם שגוי, המשחק עובר ל-`failed` ומסתיים מיד.  
5. אם הרצף כולו שוחזר נכון, השלב הושלם. אם זהו שלב 10, עוברים ל-`won`; אחרת מוסיפים צבע אקראי ומציגים את הרצף הבא.

#### **שמירת תוצאה**

1. עם הכניסה הראשונה למצב `failed` או `won`, נוצרת רשומת משחק.  
2. ה-Storage Module שומר את הרשומה ומעדכן את השיא האישי אם הניקוד גבוה יותר.  
3. ה-UI מציג את הניקוד הסופי ואת המשוב המתאים.  
4. מסך "אודות" קורא את ההיסטוריה ואת השיא מה-Storage Module.

### **2.5 ממשקי API ותקשורת**

* אין API פנימי בין Frontend ל-Backend.  
* אין שירותי API חיצוניים.  
* המודולים מתקשרים באמצעות פעולות ואירועים בתוך האפליקציה.  
* Web Audio API משמש ליצירת הצלילים.  
* Web Storage API משמש לשמירת התוצאות.  
* Service Worker ו-Cache API משמשים לאחסון משאבי האפליקציה לצורך שימוש Offline.

### **2.6 אימות, הרשאה, אבטחה ופרטיות**

* אין אימות או הרשאה, משום שאין חשבונות או נתונים מרוחקים.  
* אין סודות, מפתחות API או גישה פרטית שיש לשמור.  
* נתוני המשחקים נשארים בדפדפן של המשתמש ואינם נשלחים לשרת.  
* `localStorage` אינו כספת מאובטחת: יש לשמור בו רק נתוני משחק שאינם רגישים.  
* האתר יוגש ב-HTTPS דרך GitHub Pages, הנדרש גם לשימוש ב-Service Worker בסביבת Production. \[3\]  
* אין להציג נתונים שנקראו מ-`localStorage` בלי לבדוק את תקינותם, ויש לטפל בשגיאות אחסון.

### **2.7 אירוח, בנייה ופריסה**

#### **Repository**

* קוד המקור ינוהל ב-Git Repository ב-GitHub.  
* ענף `main` יהיה הענף שממנו מתבצעת פריסת ה-Production.  
* קובצי המקור, הגדרות Vite, הבדיקות והגדרות ה-PWA יישמרו ב-Repository.  
* תיקיית `dist` היא תוצר Build ולא מקור האמת; אין לערוך אותה ידנית.

#### **Build ופריסה אוטומטית**

1. שינויי קוד נשלחים ל-GitHub באמצעות Push או Merge ל-`main`.  
2. GitHub Actions מתקין את התלויות מתוך קובץ הנעילה (lock file) של מנהל החבילות.  
3. מופעלות בדיקות לוגיקה ובדיקת Build.  
4. Vite בונה את האתר לתיקיית `dist`.  
5. GitHub Actions מעלה את התוצר ל-GitHub Pages.  
6. GitHub Pages מפרסם את הגרסה החדשה ב-HTTPS.

יש להגדיר ב-GitHub: **Settings ← Pages ← Build and deployment ← Source: GitHub Actions**. \[6\]\[7\]

#### **הגדרת נתיב פרסום**

אם האתר מתפרסם בכתובת `https://<username>.github.io/<repository>/`, יש להגדיר את `base` של Vite לנתיב `/<repository>/`. אם הוא מתפרסם תחת דומיין המשתמש `https://<username>.github.io/` או תחת דומיין מותאם, יש להגדיר `base: '/'`. הגדרה שגויה עלולה לגרום לכך שקובצי JavaScript, CSS או סמלי PWA לא ייטענו. \[7\]

#### **תצורה**

* אין משתני סביבה סודיים או גישה פרטית ל-Production.  
* שם/נתיב ה-Repository, פרטי ה-Manifest ופרמטרי ה-Build הם תצורה ציבורית ואינם סודות.  
* הרשאות GitHub Actions יוגבלו להרשאות הנדרשות לפרסום ב-Pages בלבד.

## החלטות מרכזיות (ADRs)

### ADR-1: ניתוב מבוסס hash
**הקשר:** לאפליקציה שני מסכים בלבד (בית ואודות), והיא מתארחת ב-GitHub Pages, שאינו תומך בהפניית כל הכתובות ל-`index.html`.
**החלטה:** ניתוב פשוט מבוסס hash, בלי ספרייה: `#/` למסך הבית, `#/about` למסך אודות, ו-`#/about?best` לפתיחת אודות ישירות בכרטיס השיא האישי. כתובת לא מוכרת מחזירה למסך הבית.
**השלכות:** אין צורך בהגדרות שרת או בדף 404 מיוחד; כפתור "אחורה" של הדפדפן ורענון הדף עובדים בכל מסך. הכתובות כוללות `#`.

### ADR-2: גופן ואיורים מקומיים בלבד
**הקשר:** המשחק צריך לעבוד Offline לאחר התקנה (Milestone 4), וסעיף 2.2 אוסר להסתמך על משאבים מ-CDN בזמן ריצה. קובץ `spec/illustrations.png` קטן, עם רקע לבן וכמה איורים יחד, ולכן אינו מתאים לשימוש ישיר.
**החלטה:** הגופן Heebo נטען מהחבילה `@fontsource/heebo` (משקלים 400–700) ונארז עם האתר. האייקונים, משטח הכוכב בתחתית וכוכבי הלכת הקטנים נוצרים בקוד (SVG/CSS) לפי ה-Mockups. האסטרונאוט, הערפילית ותמונת הכוכבים נגזרו מתמונת ייחוס שסיפקה המשתמשת ונשמרים כקובצי WebP ב-`src/assets/`. השביט וכוכבי הלכת מאותה תמונה לא נכללו, כי מופיע עליהם סימן מים של Canva.
**השלכות:** אין בקשות רשת חיצוניות; כל המשאבים נכללים ב-Build ויהיו זמינים לשמירה מראש ב-Service Worker. איכות האיורים מוגבלת לרזולוציה של תמונת הייחוס.

### ADR-3: מנוע משחק טהור ותזמון במסך הבית
**הקשר:** צריך לבדוק את כללי המשחק (רצף, ניקוד, ניצחון/כישלון) בבדיקות אוטומטיות, בלי דפדפן ובלי להמתין לאנימציות.
**החלטה:** `src/game/engine.ts` מכיל את כללי המשחק בלבד — בלי DOM, בלי טיימרים ובלי צלילים — ומקבל את פונקציית האקראיות כפרמטר. התזמון (הצגת הרצף, השהיות, משוב הצלחה) וההשמעה נמצאים ב-`src/screens/home.ts`, וכל הטיימרים מבוטלים כשמתחיל משחק חדש או כשעוזבים את המסך (הנתב קורא ל-`destroy` של המסך).
**השלכות:** כללי המשחק נבדקים ב-Vitest (`npm test`); שינוי קצב הרצף נעשה בקבועים בראש `home.ts`. מעבר למסך „אודות” באמצע משחק מסיים אותו, בהתאם ל-PRD (אין שמירת משחק פעיל).

### ADR-4: מודול אחסון עם Storage מוזרק
**הקשר:** צריך לשמור תוצאות ב-`localStorage`, להתמודד עם אחסון חסום, מלא או פגום, ולבדוק את ההתנהגות הזו אוטומטית בלי דפדפן.
**החלטה:** `src/storage/history.ts` מרכז את כל הגישה לאחסון ומקבל אובייקט אחסון כפרמטר אופציונלי (ברירת מחדל `localStorage`). רשומות שנקראות עוברות בדיקת מבנה ורשומות פגומות מסוננות. `saveGame` מחזיר `true` רק אם ההיסטוריה נכתבה בפועל, ומסך הבית מציג הודעה כשהשמירה נכשלת. השיא האישי מחושב כמקסימום בין `simon.bestScore.v1` לניקוד הגבוה בהיסטוריה. החץ בשורות ההיסטוריה במסך „אודות” הוא קישוט בלבד, כי אין מסך פרטי משחק. בשורה מוצג גם שלב הסיום („כישלון · שלב 3”), כנדרש ב-PRD.
**השלכות:** הבדיקות ב-`src/storage/history.test.ts` מכסות שמירה, שיא, נתונים פגומים ושגיאות אחסון. כשהאחסון אינו נגיש, השיא מוצג כ-„—”. ההיסטוריה אינה מוגבלת בגודלה.
