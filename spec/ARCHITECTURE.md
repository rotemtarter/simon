### **1.2 החלטות טכנולוגיות מרכזיות**

* **TypeScript ללא תגובה:** נבנה ממשק קטן עם שני מסכים ומספר מצבי משחק מוגדרים. Vanilla TypeScript מספיק סיבה, ומונע הוספת שכבת רכיבים ותלויות שאינן נחוצות. תגובה תהיה חלופה סבירה אם המוצר יוסיף עוד למכלול מורכב יותר, אך אינו בגרסה הנוכחית.  
* **Vite במקום פיתוח בנייה ידני:** מספק סביבת ובניית ייצור סטטית עם מעט תצורה. לפי התיעוד, `vite build` מפיק חבילה שמתאימה לאירוח סטטי. \[1\]  
* **`vite-plugin-pwa` במקום כתיבת Service Worker מאפס:** מפשט יצירת מניפסט, Service Worker ושמירת משאבים לשימוש לא מקוון. יש להגדיר בפורש את המשאבים הקריטיים שיישמרו מראש. \[2\]\[3\]  
* **Web Audio API במקום ספריית אודיו:** ארבעת הצלילים פשוטים וניתן אותם באמצעות צמתי מתנד/הגבר. כך אין צורך להוריד את קובצי שמע, והצלילים זמינים גם במצב לא מקוון. ה-API זמין באופן רחב בדפדפנים מודרניים. \[4\]  
* **`localStorage` במקום מסד נתונים או IndexedDB:** קטנים ומובנים כרשומות משחק, `localStorage` מספיק. הוא נשמר בין הפעלות דפדפן, אך הוא מקומי למקור/דפדפןנו מסנכרן נתונים ואי בין מכשירים. יש מצב שבו הגישה אליו נכשלת. \[5\]  
* **דפי GitHub במקום Vercel או שרת:** האתר הוא Frontend סטטי בלבד. דפי GitHub ו-GitHub Actions מאפשרים לבנות ופריסה אוטומטיים מה-Repository, ללא Backend. יש להגדיר את `הבסיס` של Vite בהתאם לכתובת הפרויקט ב-GitHub Pages. \[6\]\[7\]

  ### **1.4 סיכונים ומגבלות**

* **אחסון מקומי:** ניקוי נתוני הדפדפן, שימוש במצב פרטי או שינוי דפדפן/מכשירים לגרום לאובדן ההיסטוריה. אין גיבוי או סנכרון.  
* **מגבלות דפדפן:** התקנת PWA ותנאי הצגת בקשת ההתקנה משתנים בין דפדפנים ומערכות הפעלה. האתר עדיין צריך לפעול כאתר רגיל גם אם התקנה אינה מוצעת.  
* **שמע: הפעלת עד** שמע יכול להיות חסום לאינטראקציה של המשתמש. יש ליצור או להפעיל את `AudioContext` בעקבות לחיצה על "התחל" ולבדוק את ההתנהגות במכשירי iOS ו-Android. \[4\]  
* **עדכוני PWA:** Service Worker יכול להמשיך להגיש גרסה שמורה עד להשלמת עדכון. יש להגדיר עדכון מדיניות ברורה ולבדוק שלא נוצרה תערובת של קובצי גרסאות שונות.  
* **דפי GitHub:** מתאים לאתר סטטי ולא להרצת Backend. יש לו מגבלות שימוש, הוא אינו מיועד לאתרי מסחר או ל-SaaS. עבור משחק אישי קטן, אתר סטטי הוא התאמה טובה. \[8\]

  ## **2\. ארכיטקטורת מערכת**

  ### **2.1 מבט כללי**

המערכת היא אפליקציית אינטרנט סטטית שרצה כולה בדפדפן. אין אחורי, מסד נתונים, Authentication, API חיצוני או שירות AI.

* GitHub Repository  
*        │ Push ל-main  
*        ▼  
* GitHub Actions  
*   ├─ התקנת תלויות  
*   ├─ בדיקות לוגיקה  
*   ├─ Vite Build  
*   └─ פרסום תיקיית dist  
*        │  
*        ▼  
* GitHub Pages (HTTPS)  
*        │ טעינה ראשונה / עדכון  
*        ▼  
* דפדפן במכשיר נייד  
*   ├─ UI: מסך בית / מסך אודות  
*   ├─ Game Engine: רצף, שלבים, ניקוד ומצב משחק  
*   ├─ Audio Module: Web Audio API  
*   ├─ Storage Module: localStorage  
    └─ Service Worker \+ Cache: שימוש Offline

  ### **2.2 חלוקה ל־מודולים**

  #### **מודול ממשק משתמש**

אחראי להצגת שני המסכים בלבד:

* **מסך בית:** לוח ארבעת הצבעים, מצב/שלב המשחק, הניקוד וכפתור "התחל".  
* **מסך אודות:** ההיסטורית המשחקים האישיים.  
* **מצב סיום בתוך מסך הבית:** הודעת כישלון או ניצחון, ניקוד סופי ואפשרות להתחיל משחק חדש. מצב זה אינו מסך ניווט שלישי.

כל הטקסטים יהיו בעברית, והפריסה תהיה RTL ו-Mobile-First.

#### **מודול מנוע המשחק**

אחראי לכללי המשחק ואינו תלוי ב-DOM:

* יצירה רצף אקראי.  
* התחלה בהתחלה עם צבע אחד.  
* הוספת צבע אחד לרצף לאחר הצלחת שלב.  
* הצגת עד 10 שלבים.  
* בדיקת לחיצות משתמש מול הרצף.  
* חסימת קלט בזמן הצגת הרצף.  
* הוספת נקודה לכל צבע ששוחזר נכון, גם אם משתמש טועה בהמשך אותו שלב.  
* סיום מיידי בטעות הראשונה, או ניצחון לאחר השלמת השלב העשירי.

מצבי משחק הלוגיים המומלצים: `idle` , `showing-sequence` , `awaiting-input` , `failed` , `won` . יש לרכז את המעברים בין בלוגית המשחק כדי למנוע קלט במצב לא תקין.

#### **מודול אודיו**

* יוצר `AudioContext` אחד ומשתמש בו לאורך המשחק.  
* מקצה תדר/צליל ייחודי לכל אחד מארבעת הצבעים.  
* מפעיל את הצליל יחד עם הדלקת הצבע.  
* מספק צלילי משוב להצלחה ולכישלון.  
* מפעיל/מחדש את `AudioContext` בעקבות אינטראקציה מפורשת של המשתמש, לפי מגבלות הדפדפן.

  #### **מודול אחסון**

* קורא וכותב את היסטוריית המשחקים והשיא האישי דרך `localStorage` .  
* מרכז את שמות המפתחות ואת פעולות הקריאה/כתיבה במקום אחד.  
* ניתוח ניתוח ובדיקת מבנה לנתונים שנקראו לפני השימוש בהם.  
* מטפל בשגיאות קריאה/כתיבה ואפשר להמשיך לשחק גם אם השמירה אינה זמינה, תוך הצגת הודעה מתאימה.

  #### **מודול PWA**

* כולל Web App Manifest שם עם האפליקציה, סמלים, צבעי תצוגה ו- `start_url` מתאים.  
* Service Worker שומר מראש את HTML, JavaScript, CSS, סמלי האפליקציה וכל משאב מקומי חיוני.  
* אין להסתמך על גופנים, תמונות, ספריות או קובצי שמע שמגיעים מ-CDN חיצוני בזמן ריצה.  
* עדכון גרסה יחליף את המטמון באופן מבוקר, בלי להשאיר את האפליקציה במצב שבו קובצי JavaScript ו־HTML לא תואמים.

  ### **2.3 מודל נתונים ואחסון מקומי**

אין מסד נתונים. כל נשמרים ב- `localStorage` של מקור האתר.

#### **רשות משחק**

כל משחק שהסתיים נשמר כרשומהת:

| שדה | סוג מומלץ | משמעות |
| ----- | ----- | ----- |
| `תְעוּדַת זֶהוּת` | חוּט | מזהה מקומית ייחודית לרשומה. |
| `הסתיים ב-` | מחרוזת בפורמט ISO 8601 | תאריך ושעת סיום המשחק. |
| `צִיוּן` | מִספָּר | מספר הלחיצות הנכונות שנצברו במשחק. |
| `רמה סופית` | מִספָּר | השלב שבו המשחק הסתיים. |
| `תוֹצָאָה` | `ניצח` או `הפסיד` | ניצחון או כישלון. |

#### **מפתחות אהסון**

* `simon.gameHistory.v1` — מערך רשומות המשחקים.  
* `simon.bestScore.v1` — שיא אישי מספרי.

יש לשמור את הרשומה פעם אחת בלבד בזמן משחק. יש מניעת שמירה כפולה עקב לחי חוזרות או המשך כפול מצב סיום. במקרה ניצחון, `finalLevel` יהיה 10; במקרה כישלון, יהיה מספר השלב שבו התרחשו הטעות.

היסטוריית המשחקים יכולה לגדול עם הזמן. בגרסה הראשונה ניתן לשמור את כל הרשומות בהתאם ל-PRD; אם יתגלה בהגבלת גודל, יש להגדיר מדיניות מפורשת ולא למחוק היסטוריה בשקט.

### **2.4 זרימת נתונים**

#### **התחל"ת משחק**

1. משתמש לוחץ על "התחל".  
2. ה-UI מבקש מה-Game Engine לאתחל משחק חדש.  
3. הניקוד, השלב והרצף הקודם מתאפסים.  
4. נוצר צבע ראשון אקראי.  
5. ה-Game Engine עובר ל- `showing-sequence` ומורה ל-UI ול-Audio Module להציג ולהשמיע כל צבע בתורו.  
6. בסיום הרצף עוברת ל- `awaiting-input` ומאפשרת לחיצות.

   #### **שחזור רצף**

1. לחיצה על צבע מתקבלת רק במצב `ממתין לקלט` .  
2. ה-Game Engine משווה את הצבע שנבחר לצבע הבא ברצף.  
3. אם נכון, הניקוד עולה באחד ומתקדמים למיקום הבא ברצף.  
4. אם שגוי, המשחק עובר ל- `נכשל` ומסתיים מיד.  
5. אם הרצף כולו שוחזר נכון, השלב הושלם. אם זהו שלב 10, עוברים ל- `וון` ; אחרת שונה צבע אקראי ומציגים את הרצף הבא.

   #### **שמירת תוצאה**

1. עם הכניסה הראשונה למצב `נכשל` או `זכה` , נוצרה רקמת משחק.  
2. ה-Storage Module שומר את הרשומה ומעדכן את השיא האישי אם הניקוד גבוה יותר.  
3. ה-UI מציג את הניקוד הסופי והמשוב המתאים.  
4. מסך "אודות" קורא את ההיסטוריה ואת השיא מה-Storage Module.

   ### **2.5 ממשקי API ותקשורת**

* אין API פנימי בין Frontend ל-Backend.  
* אין שירותי API חיצוניים.  
* המודולים מתקשרים באמצעות פעולות ואירועים בתוך האפליקציה.  
* Web Audio API שימוש ליצירת הצלילים.  
* Web Storage API משמש לשמירת התוצאות.  
* Service Worker ו-Cache API משמשים לאחסון משאבי האפליקציה לצורך לא מקוון.

  ### **2.6 אימות, הרשאה, אבטחה ופרטיות**

* אין אימות או הרשאה, משום שאין חשבונות או נתונים מרוחקים.  
* אין סודות, מפתחות API או גישה פרטית שיש לשמור.  
* נתוני המשחקים נשארים בדפדפן של המשתמש ואינם נשלחים לשרת אפליקציה.  
* `localStorage` אינו כספת מאובטחת: יש לשמור בו רק נתוני משחק רגישים.  
* האתר יוגש ב-HTTPS דרך GitHub Pages, נוסף גם לשימוש ב-Service Worker בסת Production. \[3\]  
* יש הצגת נתונים שנקראו מ- `localStorage` בלי בדיקת תקינותם, ולטפל בשגיאות אחסון.

  ### **2.7 אירוח, בנייה ופריסה**

  #### **מאגר**

* קוד המקור ינוהל ב-Git Repository ב-GitHub.  
* ענף `ראשי` יהיה הענף שממנו יעבודת פריסת הפקה.  
* קובצי המקור, הגדרות Vite, בדיקות והגדרות PWA יישמרו ב-Repository.  
* תיקיית `dist` היא תוצר Build ולא מקור האמת; אין צורך לערוך אותה ידנית.

  #### **בנה ופריסה אוטומטית**

1. שינוי קוד נשלחים ל-GitHub באמצעות Push או Merge ל- `main` .  
2. פעולות GitHub מתקין את התלויות מתוך קובץ הנעילה של מנהל החבילות.  
3. מופעלות בדיקות לוגיקה ובדיקת Build.  
4. Vite בונה את האתר לתיקיית `dist` .  
5. פעולות GitHub מעלה את התוצר ל-GitHub Pages.  
6. GitHub Pages פרסם את הגרסה החדשה ב-HTTPS.

יש להגדיר ב-GitHub: **הגדרות ← דפים ← בנייה ופריסה ← מקור: פעולות GitHub** . \[6\]\[7\]

#### **הגדרת נתיב פרסום**

אם האתר מתפרסם בכתובת `https://<username>.github.io/<repository>/` , יש להגדיר את `הבסיס` של Vite לנתיב `/<repository>/` . אם מתפרסם תחת דומיין משתמש `https://<username>.github.io/` או דומיין מותאם, יש להגדיר `base: '/'` . שגויה עלולה לגרום לקובצי JavaScript, CSS או סמלי PWA לא להיטען. \[7\]

#### **תצורה**

* אין משתני סביבה סודיים או גישה פרטית ל-Production.  
* שם/נתיב Repository, פרטי מניפסט ופרמטרי Build הם תצורה ציבורית ואינם סודות.  
* הרשאות GitHub Actions יוגבלו להרשאות לפרסום דפים בלבד.  
* מומלץ להריץ בדיקות ו-Build לפני שלב הפרסום, כך ששגיאות ימנעו פריסה.

  ### **2.8 בדיקות ואיכות**

* בדיקות יחידה ליצירת רצף, הוספת צבע בין שלבים, בדיקת קלט, צבירת ניקוד וסיום בניצחון/כישלון.  
* בדיקה שהקלט חסום בזמן `showing-sequence` .  
* בדיקה שלחיצה שגויה מסיימת את המשחק ושכל לחיצה נכונה עד הטעות נכללת בניקוד.  
* בדיקה שתוצאה נשמרת פעם אחת בלבד ושיא אישי מתעדכן רק כאשר הניקוד גבוה יותר.  
* בדיקת מצב היסטוריה ריקה ושגיאות `localStorage` .  
* בדיקת אופליין לאחר טעינה והתקנה: פתיחת האפליקציה, הפעלת כל ארבעת הצלילים, משחק מלא וכתיבה להיסטוריה ללא רשת.  
* בדיקות במכשירי Android ו-iOS בדפדפנים מודרניים, בדגש על התקנת PWA, RTL, גודל אזורי לחיצה והתנהגות שמע.  
* בדיקת עדכון Service Worker לאחר פרסום גרסה חדשה.

  ## **3\. רצוננות לגרסה הנוכחית**

* אין צורך בספריית AI, בשירות Analytics או באינטגרציה חיצונית.
